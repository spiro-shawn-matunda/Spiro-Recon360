# SpiroData GitHub review resolution

Reviewed on 9 October 2026 against `spiro-shawn-matunda/Spiro-Recon360`, branch `TEC-189-UI-Dashboard-Wallet-Deduction-vs-Swap-Reconciliation`.

The repository has 11 individual review issues and a summary issue. The confirmed defects have been fixed locally. Three claims do not reproduce in the existing code and are explained below. GitHub issues #1–#12 now have verified implementation and test-result comments. All remain open pending review; the code changes have not been committed or pushed. See the [GitHub summary update](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/12#issuecomment-6081394703).

| GitHub finding | Resolution |
|---|---|
| [#1 SQL template braces](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/1) | The original code is correct. The wallet template is an f-string and needs `{{filters}}`; the swap template is a normal string and needs `{filters}`. Both produce the same runtime placeholder, followed by one `.format(filters=...)` call. Changing the normal string as suggested would leave invalid braces in SQL. Regression tests exercise both groups, both detail modes and all identifier classifications. |
| [#2 detail lookup consistency](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/2) | Replaced two live detail queries with one statement and one cursor context. A materialized target CTE plus guarded reference partitions keeps duplicate checks, NULL handling and country scope within one statement snapshot. Read-only plan checks verified the active partition keeps the original indexed lookup performance. |
| [#3 update timestamp thread safety](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/3) | The original timestamp and dictionary update are correctly serialized by the same `RLock`. Moving the timestamp outside the lock could introduce stale ordering. Kept that behavior and covered concurrent updates, simultaneous commits and discard protection with regression tests. |
| [#4 swallowed import errors](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/4) | Statistics and cache failures now log tracebacks and produce `complete_with_warnings`, with warnings displayed in the dashboard. Confirmed imports stay committed; errors after commit never falsely claim rollback. The browser recognizes both successful terminal states. |
| [#5 excess query parameters](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/5) | The original `parse_qs(max_num_fields=10)` already raises `ValueError`; it does not truncate. Added an explicit maximum-parameter error and regression tests showing HTTP 400 before database access. |
| [#6 cursor validation](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/6) | Added shared format and length validation to wallet, counterpart, Due and Offer pagination, detail lookups and imported source Record Ids. Exact Zoho IDs and synthetic/local IDs remain supported. Cursor strings remain bound SQL parameters, with no authorization role. |
| [#7 job resource cleanup](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/7) | Added periodic cleanup, absolute active deadlines, expiry for abandoned receiving jobs, cancellation of queued work and cancellation requests for running database work. Running workers retain ownership of their files. Futures and connection references are released after completion. Unexpected worker failures become logged terminal states. |
| [#8 argument parsing](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/8) | All arguments now pass through one root argparse parser before dispatch. Export/import modes are mutually exclusive; mode-inappropriate, unknown and missing-value arguments fail before side effects. Existing export flags, import flags and `--port` remain available. |
| [#9 decimal validation](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/9) | Retained exact Decimal values and non-finite rejection; added PostgreSQL storage-limit validation. Validation previews and dry runs show aggregated warnings for negative values, zero transaction amounts, monetary values at least one billion source units and monetary precision beyond two decimal places. These screening thresholds do not reject legitimate ledger balances, zero-charge offers or exported Due values. Strict currency/business limits require confirmed business rules. |
| [#10 CSV formula protection](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/10) | Centralized CSV cell safety and applied it to dashboard and command-line reconciliation exports and the existing counterpart/Due/Offer export helpers. Known monetary strings bypass escaping only after finite Decimal validation; malicious amount strings are escaped. Also covered newline and space-prefixed formulas while preserving real numeric amounts. |
| [#11 database error logging](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/11) | Database requests log tracebacks with method, route and SQLSTATE. Responses distinguish timeout, permissions, concurrency and connection failures without returning raw database exception details. Import and startup failures are logged too. |

The additional items in [summary issue #12](https://github.com/spiro-shawn-matunda/Spiro-Recon360/issues/12) were checked:

- Upload reads now reset a two-minute idle timeout as chunks arrive. Status polling backs off and retries transient failures up to five times, without replaying upload or commit POSTs.
- Discard and abort cannot remove files owned by queued/running workers; job transitions remain locked.
- Worker futures, progress closures and connection references are released after completion. A standalone progress-callback leak was not reproduced.
- Missing static assets fail startup clearly; an asset removed during runtime produces a logged HTTP 503.
- Removed the unused `Path` import from the dashboard and centralized repeated session/busy error messages.
- CSRF comparison already uses `secrets.compare_digest` before any upload reservation, body read or import mutation. Regression coverage verifies this order; rejected POSTs now close the connection.

Validation: the full unit and PostgreSQL integration suite passed **103 tests with no skips** in a newly created local disposable database containing synthetic fixtures. The test database was removed afterward. JavaScript syntax checks and frontend polling checks also passed. Read-only execution plans compared the original and guarded detail lookup at approximately **225 ms each** on the loaded data; that is a representative local measurement, not a general performance guarantee.
